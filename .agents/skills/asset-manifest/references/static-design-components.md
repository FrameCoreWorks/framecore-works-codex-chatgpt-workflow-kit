# Explicit Static Design Components

Use this reference only for an explicit separate-elements, layer-by-layer or
editable-assembly request. Ordinary graphics remain one integrated output.
A capability question needs an answer, not an asset production sequence.
This skill inventories and prepares handoffs; it does not render, composite,
compress, upload or invent an editor connection.

## Shared composition

Record one composition with goal, concept lock, canvas/coordinate system,
palette, light, perspective, reserved reading zones and full exact copy
inventory. Use `Unknown` for unresolved measurements and host/editor behavior.
Keep each component's role, placement, scale, opacity/blend intent, alpha need,
assigned copy IDs and dependencies. Keep a product and its contact shadow
together when separation would compromise the agreed realism.

An independent text-free component can omit lettering at its own scope without
erasing project-level copy. Exact editable text remains a typesetting handoff.
Do not propose a blank background plus overlays to replace an ordinary request
for a finished poster. The requesting user must explicitly choose that output.

## Versions and review

Use the [component manifest template](../templates/static-design-components.md)
within the actual project. It is not state stored inside the installed skill.
Record the actual source method as `extracted`, `reconstructed` or
`newly_generated`. Generative reconstruction of hidden content is not recovery
of original pixels or layers.

For user-requested sequential production, prepare the current component only,
then hand off to the existing execution/QA route. Keep generated status, QA
status and explicit user selection separate. Default to reviewing and selecting
that exact version before progressing; honor a different review sequence
explicitly authorized by the user. An agreed asset list alone is not evidence
that unseen outputs were accepted.

A replacement remains a candidate while the previously approved version stays
selected. Recheck dependencies after a replacement; retain unrelated approved
bytes. Resolve outstanding candidates before final packaging.

## Delivery handoff

The existing `qa-iteration` allowlist governs eligible files. Hand it to
`delivery-documentation` with selected IDs/versions, actual filenames, digests,
dimensions/alpha where inspected, and assembly instructions (order, geometry,
type specification, blend assumptions and unfinished work).

Honor the user's choice of individual files or archive. Packaging requires
actual host capability and a request; report unavailable properties rather
than creating placeholders. The delivery role must verify the exact archive
inventory and decompressed bytes against selected files. Exclude rejected
drafts, unrelated references and private sources not requested for delivery.
No cloud upload or external generation is implied.

An asset-set handoff is complete at its requested scope. It is not a verified
assembled poster, an editable layered document or a print master.
